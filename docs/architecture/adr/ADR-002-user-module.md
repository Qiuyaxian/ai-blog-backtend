# ADR-002：用户模块数据模型与权限基线

## 背景与约束

用户模块是博客系统的账号基座：文章、评论等未来业务对象都要引用用户。功能规格（`specs/001-user-module/spec.md`）已确定以下业务约束：

- 账号关键字段：`username`、`email`、`password`、`isAdmin`，以及 `createdAt` / `updatedAt`。
- `username` 与 `email` 均为系统内唯一登录标识。
- 新注册用户默认非管理员；管理员身份只能由管理员授予或回收。
- 任何时候系统必须至少保留一名管理员。
- 密码强度规则（澄清结论）：长度 8–64 位，必须同时含字母和数字，不强制特殊字符与大小写混合。
- 登录/会话/令牌签发不在本模块范围（后续认证功能承接），本模块只提供账号资料与权限判定。

工程约束（来自宪法与 ADR-001）：

- TypeScript-First：DTO / Service 入参出参显式类型，禁止 `any`。
- NestJS 业务域固定 `module / controller / service / dto / schemas` 分层；模块间只通过导出的 Service 协作。
- 密码必须 bcrypt（cost >= 10）哈希，禁止明文存储、禁止进入日志。
- MongoDB 7 + Mongoose 6 + `@nestjs/mongoose` 9；唯一约束靠数据库唯一索引，Service 层捕获 `E11000` 转业务错误（见 ADR-001 与《MongoDB + NestJS 集成设计文档》§2.4）。
- `bcrypt`、`class-validator` 与 `class-transformer` 已按 T001 经人工评审后安装（见 `package.json`）。

## 决策

### D1：单集合 `users`，角色用布尔字段 `isAdmin`，不引入角色集合

用户文档存于单一 `users` 集合。角色不建独立 `roles` 集合、不使用字符串数组，只用一个**非必填**布尔字段 `isAdmin`（缺省即 `false`，普通用户）：

- 系统当前只有"普通用户 / 管理员"两种角色，布尔字段是恰好够用的表达；角色集合属于 YAGNI。
- 未来若出现第三种角色或细粒度权限，再以 expand-contract 方式新增 `roles: string[]` 字段演进，届时另立 ADR，不在本次提前设计。

### D2：`username` 与 `email` 双登录标识，均建唯一索引并做归一化

- `username`、`email` 各建一个唯一索引。
- 归一化规则（对应规格"假设"章节）：写入前对两字段 `trim()`；`email` 用 Mongoose `lowercase: true` 落库为小写，查询同样按小写比对；`username` 保留原始大小写显示，但唯一性按**不区分大小写**判定——通过额外的归一化字段 `usernameLower`（trim + lowercase，唯一索引）实现，避免依赖不区分大小写的排序规则。
- 唯一性的最终裁决者是数据库唯一索引；Service 层对 `E11000` 按冲突字段转成"用户名已存在 / 邮箱已存在"的可区分业务错误（HTTP 409）。

### D3：密码只存 bcrypt 哈希，强度在信任边界校验

- 使用 `bcrypt`（cost >= 10）对密码做单向哈希后存入 `password` 字段；不存明文、不存可逆加密值。
- 强度规则（长度 8–64、须同时含字母和数字）在 DTO 层用 `class-validator` 校验；不信任任何越过 DTO 的输入。
- 对外返回一律走脱敏视图：响应 DTO / `toJSON` 变换中永久剔除 `password` 与 `usernameLower`，列表与详情均不返回。
- 禁止在任何日志中输出密码或哈希。

### D4：权限判定用 Guard，`isAdmin` 仅管理员（超管）可更新

- `isAdmin` 在数据层非必填、缺省为 `false`；注册 DTO 不声明该字段（白名单机制直接丢弃），新建文档统一落 `false`，杜绝权重赋值提权。
- `isAdmin` 的变更只能由管理员（超管）经专用接口完成，其他任何角色（含普通用户改自己）均无权写入该字段；Service 在"取消最后一名管理员"或"删除唯一管理员"时拒绝操作（统计未删除管理员数量），保证系统始终至少有一名未删除管理员。
- 认证态（"当前用户"）由后续登录功能提供；本模块定义 Guard 所需的角色判定接口（`RolesGuard` + `@Roles` 风格），但令牌解析本身不在本模块实现。

### D5：时间戳由 Mongoose `timestamps` 托管，删除用软删除字段 `deletedAt`

`@Schema({ timestamps: true })` 自动维护 `createdAt` / `updatedAt`，不手写赋值。用户删除采用软删除：仅管理员可置 `deletedAt`，记录物理保留（文章/评论未来引用不悬空），被删用户不可登录、不进列表；不提供硬删除与用户自助注销。本期软删用户的用户名/邮箱不释放。

## 考虑的替代方案

- **独立 `roles` 集合 + 多对多关联**：表达力强，但当前只有两角色，引入集合、关联表与同步逻辑属于过度设计；待真实权限需求出现再演进（见 D1）。
- **角色用字符串字段（如 `role: 'user' | 'admin'`）**：可扩展性略好于布尔，但规格字段已明确为 `isAdmin`，且两值场景布尔更简单；字符串枚举留作未来演进选项。
- **仅靠应用层查重保证唯一**：并发下会漏（两个请求同时查不到、同时插入）。唯一索引是并发安全的唯一可靠裁决层，应用层查重只用于优化错误提示。
- **`argon2` 替代 bcrypt**：argon2 抗 GPU 破解更强，但宪法已硬性指定 bcrypt（cost >= 10）；更换算法需要先修宪，不在本功能范围。
- **邮箱大小写敏感、不归一化**：会允许 `a@x.com` 与 `A@x.com` 注册成两个账号，违背用户对"同一邮箱"的常识，也会被邮件投递行为打脸，故不采用。

## 重新评估条件

- 出现第三种角色或需要资源级细粒度权限时：重新评估 D1，演进为 `roles` / 权限表。
- 登录体系改用第三方身份提供方（SSO/OAuth）为主、本地密码为辅时：重新评估 D3 的密码字段必填性与账号合并规则。
- 安全策略升级（宪法允许 argon2 或引入密码哈希 pepper 管理）时：重新评估 D3 的哈希算法，按 expand-contract 支持双哈希平滑迁移。
- 需要账号停用/注销/邮箱找回流程时：增补状态字段与凭据生命周期 ADR，本 ADR 不预先覆盖。

## 后果

### 正面

- 模型最小：一个集合 + 一个布尔角色字段，覆盖全部现行需求，学习与测试成本低。
- 唯一性由数据库兜底，并发注册安全；错误提示按冲突字段区分，体验清晰。
- 密码安全与宪法一致（bcrypt + 永不外泄），信任边界统一在 DTO 校验。
- 时间戳零样板，自动一致。

### 负面

- `isAdmin` 布尔模型表达不了三值以上角色，未来扩展需一次 schema 演进（已在 D1 预留路径）。
- `usernameLower` 是为大小写不敏感唯一性引入的冗余字段，需保证注册与改名两条写路径都正确维护。
- "至少一名管理员"靠应用层统计 + 拒绝实现，极端并发下两个管理员同时被降权存在理论竞态；当前博客规模与管理员操作频率下可接受，缓解措施与上限见设计文档并发小节。

### 中性

- 已新增 `bcrypt` 与 `class-validator`（含 `class-transformer`）依赖，T001 已完成人工评审并安装。
- Guard 角色判定接口先落地、认证态提供者后落地，两者之间需要一个临时的请求用户注入约定，由设计文档明确。
