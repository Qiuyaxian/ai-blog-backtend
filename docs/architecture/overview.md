## 项目简介

Blog 博客系统面向内容创作者、访客和平台管理员，提供文章发布、分类标签、评论互动、用户认证、点赞收藏、热门排行和基础搜索能力。系统需要支撑文章读多写少的典型博客场景，同时保证内容数据持久可靠、热点内容访问低延迟、用户认证安全可撤销。

## 系统上下文

```mermaid
graph LR
    Visitor([访客]) -->|浏览 / 搜索 / 评论| Sys[Blog 后端系统]
    Author([作者]) -->|发文 / 管理自己的内容| Sys
    Admin([管理员]) -->|审核 / 用户与权限管理| Sys
    Sys -->[(MongoDB)]
    Sys -->[(Redis)]
    Sys -. SMTP .-> Mail[邮件服务]
```

| 外部参与者      | 与系统关系                                       |
| --------------- | ------------------------------------------------ |
| 访客            | 以只读为主，可浏览、搜索、评论；部分内容无需登录 |
| 作者            | 认证后发布、编辑自己的文章                       |
| 管理员          | 内容审核、全量管理、用户与权限管理               |
| MongoDB / Redis | 内部基础设施，仅后端可访问，不对用户暴露         |
| 邮件服务        | 出站发送邀请 / 通知，异步调用                    |

**边界约束**：所有外部请求只经后端系统，MongoDB / Redis 不直接暴露给用户；邮件等外部调用失败须降级或异步重试，不阻塞主流程。

## 关键质量属性

> 本节定义系统在功能之外必须满足的质量目标，作为架构取舍和验收的依据。
> 目标值为当前基线（状态 Draft，未接入度量前不作为强制门槛）；阈值、告警与 SLO 的唯一权威定义见 [可观测性](../operations/observability.md)。

| 质量属性                 | 含义                     | 目标 / 策略                                     | 主要手段                                        |
| ------------------------ | ------------------------ | ----------------------------------------------- | ----------------------------------------------- |
| 可用性 Availability      | 服务可正常访问的时间占比 | 月度可用性 ≥ 99.9%                              | 健康检查、无状态多实例、故障自动重启、降级页    |
| 性能 Performance         | 请求响应速度与吞吐       | 核心读接口 P95 ≤ 200ms、P99 ≤ 500ms；热点走缓存 | Redis 缓存、索引优化、分页、连接池              |
| 可伸缩性 Scalability     | 负载增长时扩容能力       | 支持水平扩容应用层；数据量增长可分片            | 无状态服务、会话外置 Redis、读写分离/分片预留   |
| 可靠性 Reliability       | 故障下不丢数据、结果一致 | 写操作持久化确认；缓存故障不影响主流程          | 写库确认、缓存降级、重试与幂等、数据备份        |
| 安全性 Security          | 抗攻击、数据不泄露       | 认证授权默认开启、无明文敏感数据                | JWT + RBAC、bcrypt、HTTPS、输入校验、限流、审计 |
| 可维护性 Maintainability | 改代码的成本与风险       | 单测覆盖率目标 80%；模块高内聚低耦合            | 分层架构、统一规范、ESLint、代码评审            |
| 可观测性 Observability   | 出问题能快速定位         | 关键链路 100% 可追踪                            | 结构化日志、指标、分布式追踪、告警              |
| 可部署性 Deployability   | 发布频率与回滚速度       | 支持灰度、回滚 ≤ 5 分钟                         | 容器化、CI/CD、expand-contract、功能开关        |

**优先级取舍**：读多写少的博客场景下，性能与可用性优先；其次安全与可观测性；可伸缩性按实际用户量演进，不提前过度设计（见架构原则“演进式架构”）。

**度量与验收**：上表目标值须由监控数据验证，禁止凭主观判断声称达标；阈值、看板与告警规则在可观测性文档落地后，本节状态由 Draft 转 Confirmed。

## 架构核心

### 架构目标

在保证可维护、可观测、可回滚的前提下，优先使用成熟组件，按业务域组织 NestJS 代码、逐步演进的场景。

### 架构原则

> 以下每条只保留原则。落地要求按“何时读 / 读什么”路由到对应文档，AI 按任务命中，不必全读。

#### 领域边界清晰

- 原则：按业务域划分 NestJS 模块，模块内高内聚，模块间低耦合。
- 何时读：新增模块、拆分模块、修改跨模块调用、新增分层时。
- 读什么：[Coding 规范 - 模块与分层规范](./development-standards.md#架构编码规范)：模块列表、分层职责、跨模块协作规则。

#### 优先成熟组件

- 原则：优先使用 NestJS、MongoDB、Redis 等成熟生态，避免过度自研。
- 何时读：引入新依赖、评估自研、替换组件时。
- 读什么：[Coding 规范 - 依赖与技术选型](./development-standards.md#2-依赖与技术选型)：评估清单、依赖管理、ADR 要求。

#### 读多写少场景优先缓存

- 原则：读多写少系统应优先缓存高频访问数据，缓存是核心设计。
- 何时读：写缓存 Key、设 TTL、处理缓存更新、排查缓存穿透/击穿/雪崩时。
- 读什么：[Coding 规范 - 缓存编码规范](./development-standards.md#3-缓存编码规范)：Key 格式、TTL 分级、更新策略、防护策略、实现约定、禁止事项。

#### 关键链路可观测

- 原则：关键链路具备日志、指标、追踪和告警。
- 何时读：新增接口、新增外部调用、接入日志/指标/Trace、配置告警时。
- 读什么：
  - 开发接入：[Coding 规范 - 可观测性编码规范](./development-standards.md#4-可观测性编码规范)：日志字段、关键指标、追踪采样、告警协同。
  - 运维配置：[可观测性](../operations/observability.md)：采集、Dashboard、告警规则、SLO/SLI、Runbook。

#### 可回滚、可灰度

- 原则：变更应支持灰度发布和快速回滚。
- 何时读：新增功能、改数据库、改 API、准备发布时。
- 读什么：
  - 发布回滚：[部署与运行](../operations/deployment.md)：蓝绿、金丝雀、回滚条件与步骤。
  - 数据库兼容与功能开关：[Coding 规范 - 可回滚与灰度编码规范](./development-standards.md#5-可回滚与灰度编码规范)：expand-contract、向后兼容、功能开关约定。

#### 安全与合规默认开启

- 原则：认证、授权、输入校验、限流和审计作为默认要求。
- 何时读：新增接口、新增 DTO、处理认证授权、写审计日志、准备上线时。
- 读什么：
  - 安全编码：[Coding 规范 - 安全编码规范](./development-standards.md#6-安全编码规范)：认证授权、输入校验、密码与敏感数据、限流与令牌、审计编码、禁止事项。
  - 安全合规运维：[安全与合规](../operations/security.md)：密钥管理、审计日志运维、合规要求、安全监控与事件响应。

#### 演进式架构

- 原则：架构随业务增长逐步演进，避免一次性过度设计。
- 何时读：做架构决策、记录技术债、评估服务拆分时。
- 读什么：[Coding 规范 - 演进式架构与 ADR](./development-standards.md#7-演进式架构与-adr)：ADR 流程、技术债、拆分信号。
