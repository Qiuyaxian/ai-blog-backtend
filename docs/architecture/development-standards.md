## 1. 模块与分层规范

### 1.1 领域边界

- 按业务域划分 NestJS 模块，如 `UserModule`、`ArticleModule`、`CommentModule`、`TagModule`、`AuthModule`。
- 模块内高内聚，模块间低耦合。
- 跨模块协作优先通过 Service 或接口。
- 禁止直接操作其他模块的 Schema。
- 避免循环依赖。

### 1.2 分层职责

| 分层       | 职责                   | 约束                                                            |
| ---------- | ---------------------- | --------------------------------------------------------------- |
| Controller | 处理 HTTP 请求与响应   | 不写业务逻辑；只做参数接收、调用 Service、返回响应              |
| Service    | 业务逻辑处理           | 不依赖 HTTP；可被多个 Controller 复用                           |
| Module     | 模块组织与依赖注入     | 显式声明 imports/providers/exports；避免循环依赖                |
| Schema     | Mongoose 数据模型定义  | 定义字段、索引、时间戳；不直接暴露给 Controller                 |
| DTO        | 数据传输对象与参数校验 | 使用 class-validator/class-transformer；配合全局 ValidationPipe |

### 1.3 跨模块协作

- 跨模块调用必须通过公开 Service 或接口。
- 禁止跨模块直接注入并操作对方 Schema。
- 共享逻辑优先下沉到独立模块或工具库。
- 循环依赖必须通过重构或事件解耦解决，禁止临时绕过。

## 2. 依赖与技术选型

### 2.1 优先成熟组件

- 优先使用 NestJS、MongoDB、Redis 等成熟生态。
- 避免过度自研。
- 自研仅限核心差异化能力，且需通过 ADR 记录原因与边界。

### 2.2 新组件评估

引入新组件前必须评估：

- 稳定性与社区活跃度
- 学习、开发、运维成本
- 可观测性接入能力
- 安全性
- 退出或替换策略
- 版本锁定与升级路径

### 2.3 依赖管理

- 生产依赖锁定版本。
- 定期更新依赖并扫描漏洞。
- 基础镜像使用可信来源，定期更新。
- 禁止引入无维护、无许可证或来源不明的依赖。
- 新依赖引入前需评估，必要时写 ADR。

## 3. 缓存编码规范

### 3.1 Key 规范

- 格式：`业务:对象:标识:维度`
- 示例：
  - 文章详情：`article:detail:{id}`
  - 文章列表：`article:list:{page}:{limit}`
  - 分类字典：`category:dict`
  - 用户会话：`auth:session:{userId}`
  - 阅读计数：`article:view:{id}`
- Key 必须包含业务前缀，避免不同业务冲突。
- Key 中禁止包含明文敏感信息。
- Key 生成必须使用统一工具函数，禁止散落字符串拼接。

### 3.2 TTL 分级

- 热点数据短 TTL。
- 稳定数据长 TTL。
- TTL 必须加随机抖动，避免同一时间大量缓存同时失效。
- 推荐 TTL 范围：
  - 热点列表：30s ~ 5min
  - 文章详情：5min ~ 30min
  - 字典数据：1h ~ 24h
  - 会话令牌：按令牌有效期设置

### 3.3 更新与失效

- 先写数据库，成功后删除缓存。
- 禁止先删缓存再写数据库。
- 一致性要求高时使用延迟双删。
- 更新缓存时优先删除而不是直接覆盖。

### 3.4 防护策略

- 穿透：空值缓存 / 布隆过滤器。
- 击穿：互斥锁 / 逻辑过期。
- 雪崩：随机 TTL、多级缓存、集群。

### 3.5 代码实现约定

- 缓存读写统一封装，禁止在 Controller 中直接操作 Redis。
- Service 层负责缓存逻辑。
- 缓存 Key 生成使用统一工具函数。
- 缓存序列化统一使用 JSON。
- 缓存异常必须捕获并降级，不能因为缓存故障导致主流程失败。
- 缓存操作日志需带 `traceId`。
- 降级期间需配合数据库限流。

### 3.6 禁止事项

- 禁止把缓存当数据库用。
- 禁止无 TTL 永久缓存，除非有明确 ADR。
- 禁止先删缓存再写数据库。
- 禁止在缓存中存储明文密码、令牌、密钥等敏感信息。
- 禁止绕过统一缓存封装直接操作 Redis。

## 4. 可观测性编码规范

### 4.1 原则

- 关键链路必须具备日志、指标、追踪和告警。
- 上线前完成可观测性接入，避免“先上线后补监控”。
- 日志、指标、追踪统一携带 `traceId`，便于关联排查。
- 告警基于 SLO / 错误预算，避免无效告警。
- 可观测性数据按合规要求脱敏、留存和访问控制。

### 4.2 日志

- 工具：Pino 结构化日志。
- 格式：JSON，便于采集与检索。
- 级别：`fatal` / `error` / `warn` / `info` / `debug`。
- 生产环境默认 `info`，排查时可临时调整。
- 日志不得记录密码、令牌、密钥、完整身份证号等敏感信息。
- 字段定义、必填项、示例、采集与保留周期以运维文档为唯一权威：[日志规范 §3 日志字段](../operations/logging.md#3-日志字段)；关键字段含 `traceId`、`userId`、`path`、`method`、`duration`、`status`、`timestamp`、`service`、`env`。

### 4.3 指标

- 应用暴露 `/metrics`，由 Prometheus 抓取。
- 关键指标包括：
  - QPS
  - P95 / P99 延迟
  - 错误率
  - 缓存命中率
  - DB 慢查询
  - 连接池使用率
  - CPU / 内存
  - 登录成功/失败数
  - 文章阅读数、评论数
- 核心接口目标：
  - 文章详情页 P99 < 200ms
  - 文章列表页 P99 < 300ms
  - 登录 P99 < 500ms

### 4.4 追踪

- 标准：OpenTelemetry。
- 传播：HTTP Header 传递 `traceparent`。
- 采样：
  - 开发 / 测试：全量采样。
  - 生产：头部采样 + 错误全采，关键链路可提高采样率。
- 关键 Span：HTTP 请求、数据库查询、Redis 操作、外部依赖调用。

### 4.5 告警协同

- 告警基于 SLO / 错误预算。
- 明确阈值、持续时间、通知渠道、责任人。
- 告警需可执行，附带 Runbook 链接。
- 避免重复告警和噪音告警。
- 开发需为新增 P1/P2 告警提供排查入口和 Runbook 链接。

### 4.6 禁止事项

- 禁止记录密码、令牌、密钥等敏感信息。
- 禁止无 `traceId` 的关键链路日志。
- 禁止在循环中打印大量日志。
- 禁止把异常吞掉不记录。
- 禁止上线未接入可观测性的关键链路。

> 采集、存储、Dashboard、告警规则、SLO/SLI、Runbook 见：
> [可观测性运维](../operations/observability.md)

## 5. 可回滚与灰度编码规范

### 5.1 功能开关

- 新功能必须支持功能开关。
- 开关默认关闭，灰度后逐步放开。
- 开关必须有负责人、清理时间和默认值。

### 5.2 数据库迁移

- 迁移版本化管理。
- 采用 `expand-contract`：
  1. 先加字段或双写
  2. 再迁移数据
  3. 最后清理旧字段
- 禁止在发布中直接删除旧字段。

### 5.3 向后兼容

- API 向后兼容 1 个大版本。
- 版本化路径：`/api/v1`。
- 新增字段必须可选。
- 禁止直接修改已有字段含义。

## 6. 安全编码规范

### 6.1 认证与授权

- 使用 NestJS Guard、Pipe、Interceptor。
- 认证模型：JWT + Refresh Token。
- Access Token：短期有效，用于访问受保护接口。
- Refresh Token：长期有效，存储在 Redis，支持撤销与轮换。
- 授权模型：RBAC。
- 角色：读者、博主、管理员。
- 敏感操作需二次校验或重新认证。
- 禁止绕过 Guard 直接访问受保护资源。

### 6.2 输入校验

- 全局 `ValidationPipe`。
- DTO 白名单，禁止多余字段。
- Controller 不直接接收未校验的原始对象。
- 所有外部输入必须校验：Body、Query、Param、Header。
- 文件上传必须校验类型、大小、内容。
- 非法参数直接拒绝，不进入业务逻辑。

### 6.3 密码与敏感数据

- 密码使用 bcrypt 哈希存储（cost >= 10）。
- JWT、刷新令牌和敏感配置不得明文落库。
- 日志不得记录密码、令牌、密钥、完整身份证号等敏感信息。
- 传输加密：全站 HTTPS / TLS。
- 存储加密：敏感字段加密存储。
- 数据导出与删除需满足合规要求。

### 6.4 限流与令牌

- 结合 Redis 做限流、黑名单和令牌管理。
- 登录、注册、评论、发文章等接口必须限流。
- 令牌支持撤销、轮换和过期。
- 异常登录需触发告警。
- 限流 Key 需带业务前缀，避免冲突。

### 6.5 审计编码要求

- 记录关键操作日志，满足合规与追溯要求。
- 审计范围：
  - 登录、登出、登录失败
  - 权限变更、角色分配
  - 文章创建、更新、删除
  - 评论审核、删除
  - 用户管理操作
  - 敏感配置变更
- 审计日志至少包含：
  - `traceId`
  - `userId`
  - `action`
  - `resource`
  - `result`
  - `ip`
  - `userAgent`
  - `timestamp`
- 审计日志只追加，不允许普通管理员修改或删除。
- 保留周期按等保与合规要求执行。

### 6.6 禁止事项

- 禁止明文存储密码。
- 禁止在日志中输出敏感信息。
- 禁止绕过 Guard、Pipe、Interceptor。
- 禁止无校验直接使用外部输入。
- 禁止把密钥、令牌提交到版本库。
- 禁止在客户端信任角色或权限声明。

> 密钥管理、审计日志运维、合规要求、安全监控与事件响应见：
> [安全与合规](../operations/security.md)

## 7. 演进式架构与 ADR

### 7.1 ADR

- 关键决策和技术债必须写 ADR。
- ADR 存放于 `adr/`。

### 7.2 技术债

- 技术债进入看板，定期评估偿还优先级。
- 记录描述、影响、偿还成本、负责人、计划时间。

### 7.3 拆分信号

优先模块化单体，按阶段拆分。拆分信号：

- 独立扩缩容需求
- 独立发布需求
- 团队边界清晰
- 性能瓶颈明确
