# 功能规格说明：用户模块（User Module）

**功能分支**：`001-user-module`

**创建日期**：2026-10-13

**状态**：Confirmed（2026-10-14 评审通过）

**输入**：用户描述："帮我创建一下 user 模块的 spec，关键字段有 username，email，isAdmin，password，还有创建时间等"

## 澄清记录

### 会话 2026-10-13

- Q: 密码的最低强度规则是什么？ → A: 密码长度 8–64 位，必须同时包含字母和数字（不强制特殊字符与大小写混合）。
- Q: isAdmin 是否必填、谁能更新？ → A: isAdmin 非必填，默认 false；注册时不接受该字段，只有管理员（超管）能更新它。
- Q: 用户删除采用哪种方式？ → A: 仅管理员可删除，且为软删除：置 deletedAt 标记、保留记录，被删账号不可登录、不出现在用户列表；不做物理删除。
- Q: 用户本人"改"资料允许改哪些字段？ → A: 仅邮箱；用户名与密码本期不可由本人修改，isAdmin 仅超管可改。

## 用户场景与测试 _(强制)_

### 用户故事 1 - 用户注册（创建账号）（优先级：P1）

访客使用唯一的用户名和邮箱注册账号，设置登录密码；系统创建普通用户账号并记录创建时间。

**为何此优先级**：没有账号就不存在用户，注册是整个模块其他一切能力的前提，单独交付即构成可用的最小产品。

**独立测试**：提供合法且未被占用的用户名、邮箱与密码完成注册，能得到一个已创建、默认非管理员、带创建时间的账号，并可验证重复注册被拒绝。

**验收场景**：

1. **假设** 用户名与邮箱均未被注册，**当** 访客提交合法的用户名、邮箱、密码，**那么** 账号创建成功，账号为普通用户（非管理员），并记录账号创建时间。
2. **假设** 用户名已被占用，**当** 访客用同一用户名注册，**那么** 注册被拒绝，并明确告知用户名已存在。
3. **假设** 邮箱已被注册，**当** 访客用同一邮箱注册，**那么** 注册被拒绝，并明确告知邮箱已被注册。
4. **假设** 提交的邮箱格式非法或密码不符合最低强度要求，**当** 访客提交注册，**那么** 注册被拒绝，并逐项提示不合规字段，且不产生任何账号。

---

### 用户故事 2 - 查看与维护个人资料（优先级：P2）

已登录用户查看自己的账号资料，并能修改自己的邮箱等非身份凭证信息；密码不明文展示。

**为何此优先级**：账号创建后，用户需要确认与维护自己的资料，这是注册之后最直接的使用闭环；依赖 P1 已存在的账号。

**独立测试**：用户注册后可查看自己的资料（含用户名、邮箱、角色、创建时间，但不含明文密码），并能成功修改允许变更的字段。

**验收场景**：

1. **假设** 用户已登录，**当** 用户查看自己的资料，**那么** 能看到用户名、邮箱、是否管理员、创建时间，且任何情况下都看不到明文密码。
2. **假设** 用户已登录，**当** 用户把邮箱改成一个合法且未被他人占用的新邮箱，**那么** 修改生效，再次查看显示新邮箱。
3. **假设** 用户已登录，**当** 用户尝试把邮箱改成已被其他账号占用的邮箱，**那么** 修改被拒绝并提示邮箱已被占用，原邮箱保持不变。
4. **假设** 用户未登录，**当** 尝试查看或修改任意资料，**那么** 请求被拒绝。

---

### 用户故事 3 - 管理员管理用户（优先级：P3）

管理员查看系统中的用户（列表与单个详情），可将普通用户提升为管理员或收回管理员身份，并可软删除用户。

**为何此优先级**：角色治理与用户生命周期管理在有了账号、有了用户之后才有管理对象，属于运营层面的能力，优先级低于用户自助闭环。

**独立测试**：以管理员身份可列出用户、查看单个用户、调整某用户的管理员标记、软删除用户；以普通用户身份执行同样操作会被拒绝。

**验收场景**：

1. **假设** 操作者是管理员，**当** 查看用户列表，**那么** 能看到各未删除用户的用户名、邮箱、是否管理员、创建时间。
2. **假设** 操作者是管理员，**当** 按标识查看某个存在的用户，**那么** 能看到该用户的资料详情。
3. **假设** 操作者是管理员，**当** 将某普通用户设为管理员，**那么** 该用户的管理员标记变为真。
4. **假设** 操作者是普通用户，**当** 尝试修改他人或自己的管理员标记、查看完整用户列表或删除用户，**那么** 请求被拒绝。
5. **假设** 操作者是管理员，**当** 删除某用户，**那么** 该用户被软删除（标记为已删除、记录保留），此后不能登录且不再出现在用户列表。
6. **假设** 操作者是管理员，**当** 对一个已删除用户再次删除或查看其详情，**那么** 系统按"已不存在/已删除"处理，不重复操作。
7. **假设** 系统中只剩最后一名管理员，**当** 尝试取消其管理员身份或删除该管理员，**那么** 操作被拒绝，保证系统始终至少存在一名未删除的管理员。

---

### 边界场景

- 用户名或邮箱大小写、首尾空格不同但实质相同（如 `Name` 与 `name`）时，是否判定为重复？
- 用户改邮箱的并发请求同时命中同一邮箱时，如何保证只有一个成功？
- 注册或资料中提交超长字符、异常 Unicode（含不可见字符）时如何处理？
- 被停用或已注销的账号（如未来支持）是否仍占用用户名/邮箱，本文如何界定？
- 软删除用户的用户名/邮箱是否释放给重新注册？本期拍板：不释放（软删除记录仍保留唯一值），避免冒充与历史归属混淆；重新开放为后续功能。
- 软删除用户是否仍计入"至少一名管理员"？本期拍板：不计入；删除唯一管理员与降权一样被拒绝。
- 管理员误把自己降权或删除导致无管理员在线时的兜底（见用户故事 3 边界，至少保留一名管理员）。

## 需求 _(强制)_

### 功能需求

- **FR-001**：系统 MUST 支持以用户名、邮箱、密码创建用户账号。
- **FR-002**：用户名 MUST 在系统内唯一；邮箱 MUST 在系统内唯一。
- **FR-003**：系统 MUST 校验邮箱格式；密码 MUST 满足最低强度要求——长度 8–64 位，且必须同时包含字母和数字（不强制特殊字符与大小写混合）。
- **FR-004**：每个账号 MUST 记录创建时间；资料发生变更时 MUST 能反映最近更新时间。
- **FR-005**：`isAdmin` 字段 MUST 为非必填，缺省时为 false（普通用户）；新注册账号 MUST 为普通用户，且注册请求 MUST NOT 能设置该字段。该字段只能由管理员（超管）授予或回收，用户不能自行提升。
- **FR-006**：密码 MUST 以不可逆方式安全存储，任何接口与日志 MUST NOT 返回或输出明文密码。
- **FR-007**：系统 MUST 区分管理员与普通用户的操作权限：用户列表查看、管理员标记变更仅限管理员；普通用户仅能查看与修改本人资料。
- **FR-008**：系统 MUST 保证任何时候至少保留一名管理员，取消最后一名管理员身份的操作 MUST 被拒绝。
- **FR-009**：用户查看资料时，系统 MUST 返回用户名、邮箱、是否管理员、创建时间等资料字段，并 MUST NOT 暴露密码相关的内部存储值。
- **FR-010**：对唯一性冲突（用户名/邮箱重复）与非法输入，系统 MUST 返回明确、可区分的错误提示，且失败操作 MUST NOT 产生或破坏账号数据。
- **FR-011**：所有用户发起的查看与修改操作 MUST 经过身份识别，未认证请求 MUST 被拒绝。
- **FR-012**：管理员 MUST 能按标识查看任一未删除用户的资料详情。
- **FR-013**：管理员 MUST 能软删除用户：删除后记录保留但标记为已删除（含删除时间），被删用户 MUST NOT 能登录、MUST NOT 出现在用户列表。
- **FR-014**：用户删除 MUST NOT 物理删除记录；系统 MUST NOT 提供普通用户自助删除，删除仅限管理员。
- **FR-015**：删除操作 MUST 受"至少保留一名未删除管理员"约束；删除唯一一名管理员 MUST 被拒绝。
- **FR-016**：已删除用户视为不存在：对其详情查询、重复删除、凭据登录 MUST 按"不存在/已删除"处理。
- **FR-017**：软删除用户的用户名与邮箱在本期 MUST NOT 释放给重新注册（记录仍持有该唯一值）。

### 关键实体 _(涉及数据时包含)_

- **用户（User）**：系统中的一个账号。关键属性：
  - 用户名（username）：账号的展示与登录标识，系统内唯一。
  - 邮箱（email）：联系方式与登录标识，系统内唯一，需符合邮箱格式。
  - 是否管理员（isAdmin）：非必填，缺省为 false；仅管理员（超管）可更新，用户不可自行设置。
  - 密码（password）：仅以安全处理后的形式保存，永不明文出现；注册与修改时须满足 FR-003 的强度要求。
  - 创建时间（createdAt）：账号建立时间。
  - 更新时间（updatedAt）：资料最近一次变更时间。
  - 删除时间（deletedAt）：软删除标记，未删除时为空；仅管理员删除时写入，记录不物理清除。
  - 关系：用户本身是被评论、文章等未来业务对象引用的主体；本模块只定义用户实体，不实现这些关联对象。

## 成功标准 _(强制)_

### 可衡量结果

- **SC-001**：访客能在 2 分钟内、首次尝试即成功完成一个合法账号的注册。
- **SC-002**：100% 的重复用户名/邮箱注册尝试被拒绝，且不产生重复账号。
- **SC-003**：100% 的资料与列表响应中不包含明文密码或其内部存储值。
- **SC-004**：100% 的越权尝试（未认证访问、普通用户执行管理员操作）被拒绝。
- **SC-005**：系统在任何操作序列后都至少存在一名未删除管理员（0 次"无可用管理员"状态）。
- **SC-006**：90% 以上的注册与资料修改请求在 2 秒内得到成功或明确的失败反馈。
- **SC-007**：100% 的软删除用户不再能登录、不再出现在用户列表，且其历史记录仍被保留。
- **SC-008**：100% 的非管理员删除用户尝试被拒绝。

## 假设

- 用户名为登录标识之一；"登录/会话/令牌签发"本身不在本模块范围内，本模块只负责账号资料及其增删查改与权限判定，登录认证流程由后续功能承接（FR-011 的"身份识别"依赖该能力提供的当前用户；软删账号不得登录的判定 FR-016 也由该登录流程执行）。
- 用户名与邮箱的唯一性按"去除首尾空格后、不区分大小写"判定，避免同形重复账号；具体大小写保留策略在计划阶段细化。
- 本模块采用软删除（deletedAt 标记，仅管理员可操作），不提供账号物理删除与用户自助注销；用户名/邮箱删除后不释放，硬删除与重新注册策略留待后续功能。
- 用户本人仅可修改邮箱；用户名与密码的自助修改不在本期（改密码需旧密码验证，由后续凭据功能承接）。
- 管理员由首个种子/初始化方式产生至少一名，具体初始化方式不在本功能范围。
- 密码最低强度已在澄清记录中确定：长度 8–64 位、须同时含字母和数字；bcrypt cost 等存储参数在计划阶段按宪法要求（cost >= 10）确定。
- 用户量为博客规模，管理后台用户列表以常规分页浏览即可，无需海量检索能力。
- SC-006 的"2 秒内反馈"本期由功能测试与手工冒烟验证可用性。可观测性按宪法原则 V 的最低要求落地：访问日志拦截器为每个请求生成 `requestId` 并输出结构化日志（含耗时），关键链路可按 requestId 关联（见 plan 宪法检查 V 与 tasks T033/T034）；指标导出与跨服务 Trace 传播属统一可观测设施，另立后续功能，本期不建设。
