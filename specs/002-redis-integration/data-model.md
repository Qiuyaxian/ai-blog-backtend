# 数据模型：Redis 缓存基础设施

**日期**：2026-10-14 | **对应规格**：[spec.md](./spec.md)

> Redis 不存权威数据、不建持久 schema。本文档定义缓存条目的**逻辑形态、键命名规范与 TTL 约定**，作为各业务模块接入时必须遵守的契约。

## 1. 缓存条目（Cache Entry）

| 属性            | 说明     | 约束                                                                    |
| --------------- | -------- | ----------------------------------------------------------------------- |
| key（键）       | 条目标识 | 必须带环境前缀（客户端自动）+ 业务命名空间（调用方提供），全系统唯一    |
| value（值）     | 缓存内容 | 任意可 JSON 序列化数据；统一 JSON 编解码；不缓存含明文密码/令牌等敏感值 |
| TTL（过期时间） | 存活秒数 | **写入必填**，正整数（秒）；到期自动删除，系统不提供永久键              |

存储形态：ioredis 在真实 key 上拼接 `keyPrefix`，值以 `SET key <json> EX <ttl>` 写入。

## 2. 键命名规范

完整物理键：`<环境前缀><业务命名空间>:<业务标识>`

```text
local:user:65ab...
 local:session:<tokenId>
uat:verify-code:<email-hash>
```

约定：

1. **环境前缀**：由 `REDIS_KEY_PREFIX`（缺省 `NODE_ENV + ':'`）经 ioredis `keyPrefix` 自动添加，调用方不传、也看不到此前缀；保证环境隔离（FR-013）。
2. **业务命名空间**：调用方在 key 中以 `<域>:<标识>` 形式提供，小写、冒号分段；不同模块前缀不同（如 `user:`、`session:`），互不覆盖（spec 验收 1.5）。
3. 键只存标识，不存敏感明文（令牌类用不可猜测的随机 id，不直接用自增序列）。

## 3. TTL 约定

| 场景（后续接入参考）    | 建议 TTL    | 说明               |
| ----------------------- | ----------- | ------------------ |
| 会话/登录态（后续功能） | 分钟~小时级 | 具体由该功能规格定 |
| 验证码（后续功能）      | 分钟级      | 到期即失效         |
| 热点资料（后续功能）    | 秒~分钟级   | 可容忍短暂陈旧     |

> 本期只交付能力，不含上述业务数据。TTL 一律由写入方按数据时效性显式给出；基础设施不设"默认 TTL"，避免漏传产生长寿命键。

## 4. 状态语义（无状态机）

缓存条目只有"存在/不存在"两种可观察状态，不存在业务状态流转：

- 写入（带 TTL）→ 存在
- 到期 / 删除 → 不存在（`get` 返回 `null`）
- 删除一个不存在的键 → 幂等成功

## 5. 逻辑库与隔离

- 默认逻辑库 `db 0`，可由 `REDIS_DB` 覆盖。
- 环境隔离以 keyPrefix 为主、逻辑库为辅；不以 `FLUSHDB`/`FLUSHALL` 作为业务清理手段（破坏性，AGENTS §8 禁止破坏性命令），测试隔离用随机 key 或测试后精确 `del`。

## 6. 不做的事（FR-014）

本期不定义也不支持：分布式锁键、事务/管道、集合/有序集合/发布订阅等数据结构。后续确有需要时另立规格并扩展本数据模型。
