# 功能规格说明：Redis 缓存基础设施集成（Redis Infrastructure Integration）

**功能分支**：`feat/user_redis_init`

**创建日期**：2026-10-14

**状态**：Draft

**输入**：用户描述："创建 redis 集成"（范围澄清：本期只做 Redis 基础设施集成；登录、注册 API、登录鉴权不在本规格，由后续功能承接）

## 用户场景与测试 _(强制)_

### 用户故事 1 - 业务模块通过统一服务读写缓存（优先级：P1）

作为后端模块开发者，我需要一个可被各业务模块注入使用的统一缓存服务，用来写入、读取和删除带过期时间的临时数据，从而让后续模块（登录态、验证码、热点数据等）无需各自管理缓存连接。

**为何此优先级**：统一缓存服务是本功能存在的唯一理由；只要这一层可用，后续业务功能即可独立接入，构成最小可交付。

**独立测试**：在任意模块（或测试用例）中注入缓存服务，写入一个带过期时间的值，能读回相同内容；删除后读取结果为空；过期时间到达后值自动消失。

**验收场景**：

1. **假设** 缓存服务可用，**当** 模块写入一个键值并指定过期时间后立即读取，**那么** 能读回与写入一致的内容。
2. **假设** 某键此前已写入，**当** 模块删除该键后再读取，**那么** 读取结果为空（未命中）。
3. **假设** 某键写入时指定了较短的过期时间，**当** 过期时间到达后读取，**那么** 该键视为未命中，且不残留永久数据。
4. **假设** 读取一个从未写入的键，**当** 模块读取它，**那么** 返回明确的"未命中"结果，而不是报错。
5. **假设** 两个模块分别使用各自的键名前缀，**当** 它们读写缓存，**那么** 互不覆盖、互不干扰。

---

### 用户故事 2 - 运维通过健康检查感知缓存状态（优先级：P2）

作为运维/值班人员，我需要在现有健康检查中看到缓存服务的连通状态，以便在缓存不可用时第一时间发现，而不是等业务报错。

**为何此优先级**：缓存是支撑性设施，其可用性需要可观测；但它依赖 P1 的连接已建立，优先级次之。

**独立测试**：在缓存正常与缓存停服两种状态下分别请求健康检查，能分别得到"健康"与"不健康"且可区分的结果。

**验收场景**：

1. **假设** 缓存服务正常运行，**当** 请求系统健康检查，**那么** 缓存项报告为健康，整体健康状态正常。
2. **假设** 缓存服务已停止或无法连通，**当** 请求系统健康检查，**那么** 缓存项明确报告为不健康，整体健康状态反映该故障。
3. **假设** 缓存从正常变为不可用再恢复，**当** 依次请求健康检查，**那么** 报告状态随之变化，恢复后重新回到健康。

---

### 用户故事 3 - 连接异常时系统行为明确且可诊断（优先级：P3）

作为运维与开发者，我需要系统在缓存连接失败或中断时给出明确、可诊断的行为与日志，而不是静默失败或产生不确定状态。

**为何此优先级**：异常路径决定生产可运维性，但建立在正常读写与健康检查之上，优先级最低。

**独立测试**：在缓存不可用时启动系统或执行一次缓存操作，观察到明确的启动失败/操作报错与结构化日志，且日志不含连接密码。

**验收场景**：

1. **假设** 缓存连接配置缺失或明显非法，**当** 系统启动，**那么** 启动过程明确报告配置问题，不以默认值静默连向非预期地址。
2. **假设** 运行期间缓存连接中断，**当** 模块执行一次缓存操作，**那么** 调用方收到明确的失败结果（可感知的错误），并产生一条含连接目标（不含密码）的结构化错误日志。
3. **假设** 缓存恢复可用，**当** 再次执行缓存操作，**那么** 操作恢复成功，无需重启应用。
4. **假设** 任何一次缓存操作成功或失败，**当** 查看日志，**那么** 日志中均不出现连接密码或缓存中存放的敏感值。

---

### 边界场景

- 缓存不可用时，业务读路径是"报错"还是"降级回源数据库"？本期拍板：缓存层只负责**明确上抛失败**，是否降级由各业务模块自行决定；基础设施层不内置静默降级（避免返回不确定状态，符合宪法原则 IV）。
- 应用启动时缓存不可用：是拒绝启动还是带病启动？本期拍板：**启动即连接校验，失败则启动失败并明确报错**（fail-fast），避免运行期才暴露；健康检查同时提供运行期状态。
- 写入时未显式指定过期时间如何处理？本期拍板：统一缓存服务的写入操作**必须携带过期时间**（不提供永久写入入口），从接口层面杜绝残留永久键。
- 多个环境（local/uat/prod）共用同一缓存实例时如何隔离？通过键前缀/逻辑库编号隔离，具体方式在计划阶段定，规格只要求"环境间不得互相可见"。
- 缓存中存放的值大小异常、序列化失败时如何处理？明确报错给调用方，不吞异常。
- 键名冲突：由调用方遵守统一命名规范（前缀+业务名），缓存服务不做业务层去重。

## 需求 _(强制)_

### 功能需求

- **FR-001**：系统 MUST 提供一个统一的缓存服务，作为业务模块访问缓存的唯一入口，支持"写入（含过期时间）、读取、删除"三类基本操作。
- **FR-002**：业务模块 MUST 仅通过依赖注入获取该缓存服务；Controller 与业务代码 MUST NOT 自行创建缓存连接或直接操作缓存客户端（宪法原则 II/IV）。
- **FR-003**：缓存服务在全应用内 MUST 复用同一组受管理的连接（单例/连接池），MUST NOT 为每次操作新建连接。
- **FR-004**：每次写入操作 MUST 要求调用方显式指定过期时间（TTL）；系统 MUST NOT 提供无过期时间的永久写入入口。
- **FR-005**：读取未命中（键不存在或已过期）MUST 返回可明确区分的"未命中"结果，MUST NOT 将未命中与异常混为一谈。
- **FR-006**：删除一个不存在的键 MUST 幂等成功（不报错）。
- **FR-007**：连接信息（主机、端口、凭证、逻辑库/前缀等）MUST 经环境配置按运行环境读取（`.env.local`/`.env.uat`/`.env.production`），MUST NOT 在代码中硬编码；凭证 MUST NOT 提交到仓库。
- **FR-008**：系统启动时 MUST 对缓存连接进行校验；连接配置缺失或无法连通时 MUST 明确失败并给出可诊断信息（fail-fast）。
- **FR-009**：缓存的连通状态 MUST 纳入系统现有健康检查，能区分健康/不健康，并在运行期随实际连通情况变化。
- **FR-010**：缓存操作失败（运行期断连、超时、序列化失败等）MUST 向调用方明确上抛错误，MUST NOT 静默返回成功或不确定状态。
- **FR-011**：连接 MUST 具备中断后自动恢复的能力；缓存恢复后操作 MUST 自动成功，无需重启应用。
- **FR-012**：系统 MUST 为缓存**连接生命周期与连接错误**产生结构化日志（至少含连接目标标识 host:port:db 与错误结果），连接密码 MUST NOT 出现在日志，缓存中存放的敏感值 MUST NOT 被日志打印；本期 MUST NOT 要求对每次成功的缓存读写逐条打日志（经 HTTP 暴露的调用已由全局访问日志按请求记录，服务内部直调的逐命令日志噪音大、无业务需要，留待统一可观测设施按需开启）。
- **FR-013**：不同运行环境与不同业务模块的键 MUST 相互隔离，MUST 通过统一的键命名/前缀（必要时加逻辑库）机制保证不互相覆盖。
- **FR-014**：本功能 MUST NOT 引入超出"连接管理 + 基本读写删除 + 健康检查"之外的高级能力（分布式锁、事务、管道、发布订阅等），这些在有具体业务需求时另立功能（YAGNI）。

### 关键实体 _(涉及数据时包含)_

- **缓存条目（Cache Entry）**：存放于缓存中的一条临时数据。关键属性：
  - 键（key）：带环境与业务前缀的唯一标识，全系统遵循统一命名规范。
  - 值（value）：调用方写入的内容，由缓存服务负责序列化/反序列化；可为空（未命中）。
  - 过期时间（TTL）：写入时必填，到期后条目自动失效，系统不保留永久条目。
- **缓存连接配置（Cache Connection Configuration）**：建立连接所需的环境相关信息（主机、端口、凭证、逻辑库/前缀），按运行环境从环境配置读取，不入库。
- **缓存健康状态（Cache Health Status）**：健康检查中代表缓存连通性的状态项，取值为健康/不健康，随实际连接情况实时变化。

## 成功标准 _(强制)_

### 可衡量结果

- **SC-001**：100% 的业务模块可通过注入统一缓存服务完成"写入 → 读回一致 → 删除 → 未命中"的完整往返，无需自行管理任何连接。
- **SC-002**：100% 经缓存服务的写入都携带过期时间，系统中不存在由本服务写入的永久键（由接口约束保证）。
- **SC-003**：在缓存停服场景下，健康检查 100% 报告缓存不健康；恢复后下一次检查 100% 恢复健康。
- **SC-004**：配置缺失或缓存不可用时启动，100% 以明确错误中止，不出现"启动成功但首次调用才失败"的情况。
- **SC-005**：运行期缓存中断后恢复，无需重启应用，后续操作 100% 自动恢复成功。
- **SC-006**：抽查全部缓存相关日志，0 条包含连接密码或缓存敏感值。
- **SC-007**：不同环境/模块的键 100% 相互隔离，无互相覆盖情况。

## 假设

- 本功能只交付缓存**基础设施层**（连接管理、统一读写删除、健康检查、可观测与异常行为）；登录、注册 API、登录态/令牌鉴权、具体业务缓存（用户资料缓存、验证码等）均不在本规格，由后续功能在本层之上承接。
- 缓存中间件采用项目技术栈基线既定的 Redis（本地开发按 AGENTS.md §2.3 启动），本规格描述其对外行为，不规定客户端库与代码结构，具体选型在 plan/ADR 阶段确定；若引入新依赖须按宪法记录 ADR。
- 缓存定位为可重建的临时数据层，不作为权威数据源；宕机或清空空缓存不造成不可逆数据丢失，权威数据仍在主数据库。
- 部署规模为博客级单实例缓存，不涉及集群/哨兵/分片；多实例高可用留待后续按需演进。
- 本地与各环境有可用的 Redis 实例及对应环境配置项；配置键命名在计划阶段对齐现有配置规范。
- 健康检查沿用系统现有健康检查端点的展示形式，仅新增缓存这一检查项，不改变其他检查项语义。
- 当前分支名为 `feat/user_redis_init`，规格目录按顺序编号为 `002-redis-integration`；分支名与规格目录相互独立，后续登录鉴权功能另开规格与分支。
