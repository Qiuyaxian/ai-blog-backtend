# 进化记录 - 2026-10-26 22:10

## 1. 任务/问题场景

005-unified-response 在同一未交付 feature 内，`data` 业务载荷形态与分页风格第三次返工（T031）：

1. 初版：列表走 `_id` 游标分页 `{items, nextCursor}`，入参 `cursor/limit`。
2. T030：外壳 `code` 数字化（第二次返工，见 EVO-20261026002）。
3. T031：用户拍板 CRUD `data` 五形态——列表改页码分页 `{total,list,page,pageTotal,index}`（入参 `page/pageSize`）、删除 `{id}` 改 `null`、只读单查不存在 404 改 200+`null`。

游标 → 页码牵动 DTO、Service 取数（多取 1 条判定 → `countDocuments`+`skip/limit`）、Swagger 模型、service/DTO 单测、user-admin E2E、swagger 文档源哨兵、001/004 契约、ADR、design、coding-style。

## 2. 根因分析

- 外壳统一只规范了顶层 `{success,code,message,data}`，**未在首个列表接口（001 用户模块）落地前锁定 `data` 的载荷形态与分页风格**。顶层形状是协议层共识，载荷形状是消费侧（前端表格）契约，后者同样横切所有模块，却被当成「各接口自定」。
- 分页风格（游标 vs 页码）的驱动方是消费端组件（无限滚动 vs 表格页码），不是提供端。规划期没有「第一个列表接口即定全项目分页范式」的强约束，导致按实现者熟悉的游标落地后被前端页码需求推翻。

## 3. 最终解决方案

- T031 锁定 CRUD `data` 五形态（分页列表 / 单对象 / null 删除 / 完整对象创建更新 / 只读空结果 null），`index` 从 1 起、越界页 200+空 list，写入 ADR-006 决策 16、coding-style §1.4、001/005 契约。
- 只读与写操作对「目标不存在」语义分离：只读单查 200+`null`（空结果是正常分支），写操作 admin/delete 仍 404。

## 4. 沉淀的可执行规则

- [x] **必须**：响应结构变更特性 analyze 前，除顶层外壳字段值域（EVO-20261026002）外，还必须显式锁定 `data` 载荷形态清单与分页风格（游标/页码、入参名、缺省/封顶、空结果与越界页语义、计算字段公式）；项目内**第一个列表接口**的 spec/contract 即为全项目分页范式，后续列表接口沿用，不允许逐接口另选。缺此项不通过 analyze。归属：`agents/arch-agent/AGENTS.md` tasks 评审清单。
