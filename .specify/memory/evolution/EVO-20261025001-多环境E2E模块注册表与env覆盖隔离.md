# 进化记录 - 2026-10-25 00:40

## 1. 任务/问题场景

004-swagger-docs 的 production 404 E2E（T022）要求在同一个 Jest 进程内独立 bootstrap 一个 `NODE_ENV=production` 应用，验证 `/api-docs`、`/api-docs-json` 与 swagger-ui 静态资源全部 404。首版用例直接在测试体内改 `process.env.NODE_ENV='production'` 后动态 `import('../src/app.module')`，结果 production 应用下文档仍 200，断言失败。

调试中连续暴露两个与「同一进程模拟多环境」相关的事实：

1. `test/setup-env.ts` 作为 jest setupFiles 在任何测试模块 import 前把 `NODE_ENV` 置为 `local`；`src/app.module.ts` 顶层的 `ConfigModule.forRoot({ envFilePath: '.env.' + process.env.NODE_ENV })` 在该闭包创建时就锁定了 `.env.local`。测试体内再改 `NODE_ENV` 后 `import()` 命中已缓存的 AppModule，envFilePath 不会重算。
2. `@nestjs/config` 加载 env 文件时**不覆盖 `process.env` 中已存在的键**。`.env.local` 的 `SWAGGER_ENABLED=true` 已被前序套件读入 `process.env`，即使模块正确重载为 `.env.production`，ConfigService 仍优先返回进程环境里的 `true`，导致 production 应用文档仍开启。

## 2. 根因分析

- 规范缺口：既有 E2E 全部跑在固定 local 环境（setup-env + createTestApp），没有「同一进程内切换 NODE_ENV 验证环境相关行为」的先例与规则；测试基建文档只写了如何自举 local 应用，未记录 envFilePath 闭包与 @nestjs/config 的进程环境优先级这两个事实。
- 直接改全局 `process.env` 却不隔离模块注册表，是对 Node 模块缓存与 ConfigModule 初始化时机的错误假设，属于可复用的测试方法论缺陷，而非本功能偶发问题——任何后续「按环境关闭/开启某能力」的特性（如生产关闭某端点、按环境切限流配置）都会再踩。

## 3. 最终解决方案

production 404 用例采用两步隔离（已落地 `test/swagger-docs.e2e-spec.ts`，注释内写明原因）：

1. 在 `jest.isolateModules()` 回调内用 `require` 重新加载 AppModule/NestFactory/各全局增强与 setupSwagger，获得独立模块注册表，使 `envFilePath` 按当下 `NODE_ENV=production` 重新计算。
2. `NestFactory.create` 之前显式覆盖全部会影响该应用的 `process.env` 键：`NODE_ENV`、`MONGODB_URI`（指向 127.0.0.1/ai_blog_test，避开 .env.production 的 localhost/ai_blog 与 IPv6 坑）、Redis 五个键、以及**被测开关本身 `SWAGGER_ENABLED=false`**；afterEach 逐键恢复原值。

另补 `setupSwagger` 关闭分支的纯函数级单测（createDocument/setup 均零调用），让「生产无文档构建开销」不依赖重型 E2E 也有回归网。
