# 进化记录 - 2026-10-26 12:00

## 1. 任务/问题场景

005-unified-response 在**同一未交付 feature** 内，外壳 `code` 字段语义被推翻两次：

1. 初版：成功 `code:'SUCCESS'`，失败 `code` 为 10 个细分字符串码（`UNAUTHENTICATED`/`INVALID_CREDENTIALS`/…），HTTP 状态行另算。
2. T029：成功 HTTP 统一 200，但 `code` 仍字符串。
3. T030（本次）：用户明确「服务异常保留；服务正常期间接口成功 200，code 作为业务码要返回对应的 200/401/500」——`code` 改数字且恒等于 HTTP 状态码，10 个字符串码降为内部异常键。

每次返工都要同步 spec/FR/contract/data-model/tasks/ADR + 单测 + 5 个 E2E 套件 + Swagger schema + 下游契约指针。T030 单测/E2E 改动约 20 处断言。

## 2. 根因分析

- 规划期对响应外壳只锁定了「字段集合」（有没有 code/message/data），**没有把 `code` 的类型、值域、以及它与 HTTP 状态行的关系作为强制决策项**。「业务码」是一词多义：可以是枚举字符串、可以是 HTTP 数字、可以是独立业务编号；不写明就默认按实现者习惯选，用户复审时必然对不上预期。
- clarify 阶段问了「成功码是什么、错误保不保留 statusCode」，但没问「错误码粒度是否合并到 HTTP 状态、调用方如何区分同状态不同原因」。这是值域设计缺口，不是字段缺口。

## 3. 最终解决方案

- T030：`ApiResponse.code:number`，恒等于 HTTP 状态码；同状态细分原因交 `message`；字符串码留作内部异常键与错误目录键，不进响应体。
- 流程侧：把「code/状态字段值域与 HTTP 关系」列为响应外壳类特性 analyze 前必须显式回答的决策项。
