# 进化记录 - 2026-10-26 01:25

## 1. 任务/问题场景

005 把所有业务响应改为五字段外壳，其中 `time` 为**每请求生成**的 ISO 时间戳。E2E 迁移时出现两类可复用问题：

1. `test/auth-login.e2e-spec.ts` 原有两个安全语义的**整体全等断言**：「未知账号 401 体 ≡ 错误密码 401 体」与「锁定第 6 次 401 体 ≡ 第 1 次 401 体」（`expect(a.body).toEqual(b.body)`，目的是锁定锁定/枚举不泄漏额外信息）。新外壳后两次请求 `time` 必然不同，全等必失败。research R7 在规划期已清点到这两处，执行时按预案改为 `toMatchObject({code,data:null,path})` + `typeof time==='string'`，信息泄漏防护改由既有 `JSON.stringify(body)` 不匹配 `/LOCKED|423|remaining/` 正则承担。
2. 豁免路径（`/health/ready`）的**异常分支**此前无测试：redis-health E2E 只覆盖 200。research R4 源码核实发现 Terminus ready 失败时抛 `ServiceUnavailableException(HealthCheckResult)`，**走全局异常过滤器**——旧过滤器还把它改写成了非 Terminus 原生体（既有偏差）。若只改成功响应而不透传豁免异常体，503 探针契约就被破坏且无测试报警。

## 2. 根因分析

- 测试方法论缺口：以「整个 body 全等」表达契约等价，隐式假设 body 是静态结构；一旦引入逐请求动态字段（time/requestId/时间戳），断言锁定的就不再是真正想保护的语义。属于可复用模式缺陷——任何后续加 trace 字段、请求指纹、分页游标回显的特性都会再踩。
- 横切变更评审缺口：改全局 filter/interceptor 时容易只验证「正常请求被正确处理」，忽略豁免/异常组合分支。探针路径的失败响应同样经过异常管线这一事实没有规则要求核实。

## 3. 最终解决方案

- 全等断言改写模式（已落地 auth-login 套件两处）：对含动态字段的响应，断言稳定字段子集 `toMatchObject({code,data,path,...})`，动态字段单独断言类型（`typeof body.time === 'string'`）；原本全等承担的安全语义（不泄漏锁定信息）保留为内容正则负断言。
- 豁免异常透传（已落地 filter 单测）：豁免路径上 `ServiceUnavailableException` 经 filter 时 `getStatus()` + `getResponse()` 原样 json；新增「豁免 + Terminus 503 → body 等于原 HealthCheckResult、status 503」单测，不做脆弱的真实停 Redis E2E。
- 规划期清点（research R7 表格）逐套件列出成功侧/错误侧断言改动点，执行零返工；analyze 闸门确认。
